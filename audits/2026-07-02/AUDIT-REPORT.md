# Аудит безопасности: StableLPManager и зависимости

**Дата:** 2026-07-02
**Проект:** `uniswap-smart-wallet` (Envelop V2 / UniSmartWallet)
**Ревизия:** ветка `master`, коммит `c9cd708`
**Фокус:** ТОЛЬКО потеря средств — утечка капитала или начисленных комиссий, тихая недопоставка, уплата протокольной комиссии с принципала, блокировка/«кирпичивание» средств (DoS на выходе), ошибки учёта, искажающие оценку/маршрутизацию стоимости.

---

## 1. Область (scope)

Проаудированы контракты:

| Файл | Назначение |
|---|---|
| `src/StableLPManager.sol` | Основной объект — NFT-owned singleton (TOKEN_ID=1), клон EIP-1167, позиции с ключом `salt == poolId`, только hookless-пулы, 10% протокольная комиссия как ERC-6909 claims в неизменяемое казначейство |
| `src/StableLPFactory.sol` | Фабрика клонов EIP-1167 (CREATE2, атомарный `initialize`) |
| `src/abstract/V4PositionManager.sol` | Базовый слой V4: unlock-диспетчер, реестр позиций, swap/settle/take, примитивы `_settle`/`_take`/`_takeClaim` |
| `src/abstract/SingletonNFTOwned.sol` | Singleton-NFT авторизация + операторы |
| `src/lib/PositionMath.sol` | Snapping тиков, `requireValidTickRange`, `liquidityFromAmounts` |
| `src/lib/PositionState.sol` | View-оценка позиции (принципал + комиссии) для метаданных |
| `src/FeeRedeemer.sol` | Погашение ERC-6909 claims протокольной комиссии (`unlock → burn → take`) |

**Модель угроз.** Внешние атакующие вызвать value-функции не могут (всё за `onlyOwnerNFT` / `onlyAuthorized`, `unlockCallback` — за `msg.sender == POOL_MANAGER`). Реалистичные акторы:
(a) злонамеренный/скомпрометированный оператор (`onlyAuthorized`);
(b) поведение токена (fee-on-transfer / rebasing);
(c) чистые ошибки учёта/округления, текущие независимо от актора.
Владелец, вредящий сам себе, **находкой не считается**.

## 2. Методология

Использован многоагентный конвейр:

1. **Fan-out.** Поверхность разбита на домены (fee-accounting, reinvest-sizing, withdraw-netting, registry/factory, native/reentrancy, operator/token-highs, verify-B-fixes), каждый домен обследован независимым агентом-аудитором с прямым чтением исходного кода (не по памяти).
2. **Adversarial verification.** Каждый кандидат прогнан через трёх независимых скептиков-верификаторов; в итоговый отчёт кандидат попадает только при ≥2 из 3 голосов «реально» (реально эксплуатируемо и ведёт к потере средств в рамках модели угроз).
3. **Lead-синтез.** Оставшиеся находки консолидированы, ранжированы по серьёзности, каждый HIGH снабжён патч-скетчем с оценкой стоимости по EIP-170.

Всего: 7 доменных агентов-искателей + 10 агентов-верификаторов + lead-синтез (17 агентов). Учтён запас EIP-170 по рантайм-байткоду клона: **≈177 байт**.

## 3. Результат: находок, прошедших верификацию, — НЕТ

**Ни один кандидат не прошёл порог верификации (≥2/3).** Массив подтверждённых находок пуст. Ниже — что именно проверено и почему поверхность в части «потери средств» чистая; далее в §5 разобраны отклонённые кандидаты (включая два прежних OPEN-HIGH), в §6 — переподтверждение фиксов аудита B, в §7 — info-заметка.

### Что проверено и почему чисто

**Протокольная комиссия vs принципал (`_skimFee`, `_skimFees`, L623–637).**
Комиссия берётся исключительно из `feesAccrued` — второго возврата `modifyLiquidity`, который в v4-core содержит только начисленные fee-дельты, не принципал. Во всех местах вызова (`_addLiquidity` L400, `_pullLiquidity` L478, `_handleClaim` L505, `_handleReinvest` L533) в `_skimFees` передаётся именно `fees`, не `delta`. Принципал не облагается. Округление доли — вверх (`(_pos(fee) * BPS + 9_999) / 10_000`), в пользу протокола; переполнения нет (`_pos(fee) ≤ uint128 max`). Ским идёт через `_takeClaim` (ERC-6909), поэтому блок-лист/пауза на казначействе не может ревертнуть unlock и запереть принципал. Утечки принципала в комиссию нет.

**Выходной путь / DoS (`withdrawTo`, `_handleWithdrawTo`, `_pullLiquidity`).**
Гвард `got < int256(p.amount)` (L451–452) проверяет кредит-дельту ДО поставки, `_take` доставляет ровно `p.amount` напрямую получателю, остаток нетится назад через `_settleManaged`. Для стандартных (не-FoT) токенов недопоставки/переоценки нет. Пред-проверка `s.liquidityToPull > have` (L430) исключает попытку снять больше, чем есть.

**Учёт реестра (`_addLiquidity`, `_pullLiquidity`, `_registerSalt`/`_removeSalt`).**
`salt == poolId`, O(1)-splice по `_saltIndexPlusOne`. При падении ликвидности до нуля запись удаляется (`_pullLiquidity` L480–483). Слияние в существующую позицию (`positions[salt].liquidity += L`) корректно. Двойной регистрации salt нет (ветка `if (positions[salt].liquidity == 0)`).

**Авторизация.** `withdrawTo`/`executeEncodedTxBatch`/`setOperator`/`setPositionDescriptor` — `onlyOwnerNFT`; `allocate`/`allocateFrom`/`reinvest`/`claimFees` — `onlyAuthorized`. Оператор не имеет доступа к дренирующим капитал функциям. `_clearOperators` при передаче NFT сбрасывает делегирования; список компактен (splice-on-disable), gas-bomb на трансфере невозможен.

**`allocateFrom` snapshot-guard (L330–343).** Пре-снимок балансов всех managed-stables и пост-проверка «уменьшиться мог только `stable`» корректно предотвращают залезание в ранее внесённые средства при deposit-and-allocate.

**Reentrancy.** Все внешние value-функции (`allocate`/`allocateFrom`/`withdrawTo`/`reinvest`/`claimFees`) — `nonReentrant`. `executeEncodedTxBatch` без гварда, но `onlyOwnerNFT` (задокументировано как принятое).

**`FeeRedeemer`.** `unlock → burn(own claims) → take` нетит дельту в ноль; `redeem` — `onlyOwner`; пропуск нулевых балансов. Утечки нет.

## 5. Рассмотрено и отклонено (considered & dismissed)

### 5.1. C-H1 — Оператор sandwich через pre-swap, ограниченный только `sqrtPriceLimitX96` (без min-out/оракула)
**Серьёзность в заявке:** HIGH · **REASSESS_PRIOR** (прежний OPEN-HIGH) · **Статус: не подтверждён как НОВЫЙ, остаётся ранее принятым**
**Локация:** `src/StableLPManager.sol:370` (`_allocateLeg`), L535–536 (`_handleReinvest`).

Пре-своп в `allocate`/`reinvest` действительно ограничен только оператор-заданным `swapPriceLimit`/`sqrtPriceLimitX96`, без min-out и без внешнего оракула. Верификаторы не подтвердили это как **новую** находку: это в точности ранее задокументированный и **принятый** элемент модели (оператор доверен в пределах `onlyAuthorized`; агрегатного капа у авто-allocate нет — принято). Средства выводятся не из контракта: своп происходит внутри того же пула, а не в произвольный адрес; ущерб — только ценовое проскальзывание внутри доверенного оператору действия. Порог «новая потеря средств вне уже принятой модели» не достигнут. Реассессмент серьёзности не изменил вердикт: остаётся OPEN/ACCEPTED в прежней редакции, не переоткрывается этим отчётом.
**Рекомендация (без изменения статуса):** если доверие к оператору когда-либо будет ослаблено — добавить `minAmountOut` на пре-своп или TWAP-гвард; сейчас это осознанно вне scope.

### 5.2. C-H2 — Нет гварда fee-on-transfer/rebasing: FoT-токен ломает `_settle` (DoS выхода) и даёт тихую недопоставку в `withdrawTo`
**Серьёзность в заявке:** HIGH · **REASSESS_PRIOR** (прежний OPEN-HIGH) · **Статус: не подтверждён как НОВЫЙ, остаётся ранее принятым**
**Локация:** `src/abstract/V4PositionManager.sol:466` (`_settle`), L483–485 (`_take`).

FoT/rebasing managed-токен действительно способен ломать `_settle` (недобор к PoolManager → `CurrencyNotSettled` → реверт unlock) и приводить к недопоставке в `_take`. Верификаторы не засчитали как новое: набор пулов фиксируется владельцем в `initialize`, managed-stables — это конфиг, задаваемый владельцем; внесение FoT-токена в конфиг относится к категории «владелец вредит себе» (не находка) либо к ранее принятому пункту «нет FoT-гварда в `initialize`». Оператор не может добавить пул. Порог реалистичного недоверенного актора не достигнут. Реассессмент серьёзности вердикт не изменил: остаётся принятым/задокументированным.
**Рекомендация (без изменения статуса):** при необходимости — allow-list проверенных стейблов на уровне фабрики; на уровне контракта FoT-детект дорог по байткоду и здесь не оправдан, т.к. конфиг доверен владельцу.

### 5.3. INFO — `reinvest`/`allocate` с `minLiquidity == 0` на выведенном пуле создаёт zero-liquidity ghost-запись в `openSalts`
**Серьёзность:** INFO · **NEW** · **Статус: не подтверждён (не потеря средств)**
**Локация:** `src/StableLPManager.sol:402` (`_addLiquidity`, ветка `positions[salt].liquidity == 0`).

Если добавление (`reinvest`/`allocate`) вызывается для пула с ранее полностью выведенной позицией и итоговое `L == 0` (нет комиссий/недостаточно средств), а `minLiq == 0`, то гвард `if (L < minLiq)` (0 < 0 == false) на L391 не срабатывает, `modifyLiquidity(0)` проходит, и `_registerSalt` создаёт запись с `liquidity: 0`, оставляя ghost-элемент в `openSalts` (повторные вызовы перезаписывают `_saltIndexPlusOne`). Все три верификатора подтвердили поведение как реальное, но единогласно отклонили как потерю средств: принципал соответствует реально добавленной ликвидности (ноль), затрагивается лишь перечисление/метаданные (view). Вне фокуса «loss of funds».
**Рекомендация:** косметически — ранний возврат при `L == 0` в `_addLiquidity`; фондового риска нет.

## 6. Переподтверждение фиксов аудита B (holding)

Все четыре фикса аудита B перепроверены и **держатся**:

- **B-1 · ERC-6909 skim (блок-лист казначейства не может «кирпичить» unlock).** Подтверждено: `_skimFee` → `_takeClaim` → `currency.take(..., true)` (V4PositionManager L493–495). Ским — это `mint` ERC-6909 claims, а не ERC-20 transfer; пауза/блок-лист на `PROTOCOL_TREASURY` не участвует в пути и не может ревертнуть unlock/запереть принципал. `FeeRedeemer` погашает claims отдельно.
- **B-2 · splice-on-disable списка операторов.** Подтверждено: `SingletonNFTOwned.setOperator` при отключении вызывает `_spliceOperator` (swap-and-pop, L90–102); `_operatorList` содержит только активных операторов, `_clearOperators` (L124–133) ограничен живым числом операторов — gas-bomb на трансфере NFT невозможен.
- **B-3 · округление протокольной комиссии ВВЕРХ.** Подтверждено: `_skimFee` L633 — `(_pos(fee) * PROTOCOL_FEE_BPS + 9_999) / 10_000`, ceil в пользу протокола, sub-threshold zero-skim-утечки нет, переполнение исключено.
- **B-4 · гвард неинициализированного пула в `_addLiquidity`.** Подтверждено: L387–388 — `(uint160 sqrtP,,,) = getSlot0(id); if (sqrtP == 0) revert PoolUninitialized();`. Аналогичный гвард в `_openPosition` базового слоя (L202–203).

## 7. INFO: рассинхрон документации и кода по `ORACLE_TYPE`

**Локация:** `src/StableLPManager.sol:41` vs комментарии L40, L132.

Код объявляет `uint256 public constant ORACLE_TYPE = 3000;` (L41), тогда как doc-комментарии в двух местах утверждают `2002`:

- L40: `/// ... for oracle indexing (constant 2002).`
- L132: `/// @param oracleType The Envelop oracle type tag (ORACLE_TYPE = 2002).`

Событие `EnvelopV2OracleType(ORACLE_TYPE, "StableLPManager")` (L224) эмитится со значением **3000**, а не 2002. Это не потеря средств.

Каноническое значение — **3000** (значение константы и эмитируемого события верно); ошибочны именно комментарии L40/L132 со значением `2002`. Их следует привести к `3000` при следующей правке файла. Код (`ORACLE_TYPE = 3000`, L41) менять **не нужно**. В рамках данного аудита правка не выполнялась — только зафиксирована.

## 8. Итог

В рамках фокуса «только потеря средств» подтверждённых находок нет. Протокольная комиссия строго изолирована от принципала и берётся через ERC-6909 claims; выходной путь защищён pre-check кредит-дельты и не подвержен DoS для стандартных токенов; авторизация и очистка операторов корректны; snapshot-guard `allocateFrom` не даёт залезть в ранее внесённые средства; фиксы аудита B держатся. Оба прежних OPEN-HIGH (C-H1 sandwich, C-H2 FoT) остаются в статусе ранее принятых элементов модели угроз (доверенный оператор; конфиг пулов, задаваемый владельцем) и не переоткрываются. Единственный требующий действия пункт — info-рассинхрон `ORACLE_TYPE` (§7), фондового риска не несёт.
