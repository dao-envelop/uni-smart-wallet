# task_045 — Пороги свежести оракула: привести `heartbeat` в соответствие с реальным периодом фидов

**Ветка:** `task/045-oracle-heartbeat-bounds`
**Находка:** `qa-workspace/quality/findings/2026-08-11-arb-oracle-heartbeat-below-feed-period.md` (S2)
**Затрагивает:** `script/oracle_feeds.json`, `script/README.md`, перезаливка фидов на Arbitrum

## Симптом

На Arbitrum — единственной сети с включённым исполнением — операторские свопы ревертят примерно в
5–6 % попыток без внятной причины. Со стороны оператора это выглядит как «операция не прошла,
повтор через минуту прошёл».

## Доказательство

`ChainlinkPriceOracle` на Arbitrum (`0xf8dA8DC6d8cDCadcc96b51d5fC0Cb59EF3672005`, контракт не
верифицирован — читаем события `FeedSet(currency, aggregator, heartbeat, tokenDecimals)`):

```bash
curl -sS "https://arbitrum.blockscout.com/api/v2/addresses/0xf8dA8DC6d8cDCadcc96b51d5fC0Cb59EF3672005/logs"
```

| Валюта | Агрегатор | `heartbeat` on-chain |
|---|---|---|
| USDC `0xaf88d065…5831` | `0x50834F31…4aD3` | `0xff` = **255 с** |
| USDT | `0x3f3f5dF8…dDE7` | `0xff` = **255 с** |
| WBTC `0x2f2a2543…5b0f` | `0xd0C7101e…6d57` | `0x15180` = 86400 с |
| ETH | `0x639Fe6ab…a612` | `0x6db` = **1755 с** |

Реальный период публикации USDC/USD — восемь последних раундов фазы 2 (`0x71c7 … 0x71bf`),
`getRoundData(roundId).updatedAt`:

```bash
curl -sS -X POST https://arb1.arbitrum.io/rpc -H 'content-type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_call","params":[{"to":"0x50834F3163758fcC1Df9973b6e91f0F0F0434aD3","data":"0x9a6fc8f5<roundId 32 байта>"},"latest"]}'
```

`updatedAt`: 1786452722, 1786452451, 1786452182, 1786451911, 1786451641, 1786451371, 1786451101,
1786450831, 1786450561 → интервалы **271, 269, 271, 270, 270, 270, 270, 270 с**.

USDT (`0x3f3f5dF8…`), раунды `0x71ca / 0x71c9 / 0x71c8` → **270 с** и **268 с**.

То есть настроенный порог 255 с **систематически меньше** периода фида ~270 с.

## Корень

`script/oracle_feeds.json`, секция `42161`: у `USDC` и `USDT` записано `"heartbeat": 255`, у `BTC`,
`ETH`, `LINK` — `"heartbeat": 1755`. Остальные строки файла совпадают с опубликованными Chainlink
значениями (3600 / 86400 / 1200). Гипотеза: для этих пяти строк значение взято не из поля heartbeat
референс-директории.

Что делает контракт (`src/oracle/ChainlinkPriceOracle.sol:158`):

```solidity
if (a <= 0 || updatedAt == 0 || updatedAt > block.timestamp || block.timestamp - updatedAt > f.heartbeat) {
```

просроченный фид ⇒ «нет свежего референса» ⇒ гейт операторского свопа закрывается
(`BaseLPManager.sol:348`, fail-closed по task_031/032). Порог ниже периода публикации недостижим по
построению: фид не может быть свежее, чем он обновляется.

USDC — `currency1` во **всех четырёх** открытых позициях менеджера `arb-vol`
(`0x60723973ABF3BBC2ce7EB4400B728390D55e264b`), поэтому под гейт попадает любой операторский своп:
пресвоп в `allocate` и своп внутри `recenter`. Окно отказа ≈ 15 с из каждых 270.

## Что делать

1. **`script/oracle_feeds.json`, секция `42161`** — заменить `heartbeat` для `USDC` и `USDT` (255) и
   пересмотреть `BTC`, `ETH`, `LINK` (1755) на опубликованные Chainlink значения из
   reference-data-directory. Значения сверить заново, а не «поднять на глаз».
2. **Записать правило в шапку файла** явно: порог = опубликованный heartbeat фида, и он обязан быть
   строго больше наблюдаемого периода публикации с запасом. Сейчас шапка говорит, откуда взяты
   значения, но не говорит, каким свойством они обязаны обладать — из-за этого ошибку и не заметили
   при ревью.
3. **Перезалить фиды на Arbitrum:**
   ```bash
   forge script script/SetOracleFeeds.s.sol --rpc-url $ARB_RPC --sender $SENDER --account $KEYSTORE --broadcast
   ```
   Скрипт пропускает неизменившиеся записи (`SetOracleFeeds.s.sol:85-91`), так что прогон затронет
   только исправленные валюты. Броадкастер обязан быть владельцем оракула.
4. **Проверить остальные сети тем же критерием.** Секции `1`, `8453`, `130`, `1301` содержат
   значения 1200 / 3600 / 86400; на Base `BTC/ETH/WBTC/cbBTC` стоят 1200 — их стоит перемерить тем
   же способом, что и Arbitrum, прежде чем считать безопасными.

**Чего не делать:** не «поднимать 255 до 300». Это чинит один симптом, оставляет четыре
невыверенных значения и ничего не сообщает следующему, кто добавит сеть.

## Как проверить

**On-chain.** После перезаливки прочитать свежее событие `FeedSet` для USDC и убедиться, что
`heartbeat` больше измеренного периода. Затем измерить возраст ответа в максимуме цикла:

```bash
curl -sS -X POST https://arb1.arbitrum.io/rpc -H 'content-type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_call","params":[{"to":"0x50834F3163758fcC1Df9973b6e91f0F0F0434aD3","data":"0xfeaf968c"},"latest"]}'
```

`block.timestamp − updatedAt` в пике (~270 с) должен укладываться в новый порог с запасом.

**Тестом.** Расширить форк-тест из task_038 (оператор + Chainlink-оракул): `vm.warp` на период фида
плюс небольшой запас после последнего раунда, затем операторский своп. До фикса тест обязан падать с
закрытым гейтом на 271 с, после — проходить. Именно это отличает регрессию от «поправили число».

`forge fmt --check` и `forge build --sizes` — как обычно (CI гейтит оба); правка только в JSON и
тестах, размеры контрактов не двигаются.
