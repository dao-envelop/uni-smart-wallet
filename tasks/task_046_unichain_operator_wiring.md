# task_046 — Включение оператора на Unichain требует трёх недокументированных шагов, а выглядит как один флаг

**Ветка:** `task/046-unichain-operator-wiring`
**Находка:** `qa-workspace/quality/findings/2026-08-11-unichain-operator-loop-cannot-act.md`
**Severity:** S3 (домен B — on-chain правда)

## Симптом

`uni-stable` (`0x9f7E19B7A3fe5e767C515203446eb9A99A104970`, Unichain 130) числится в наблюдаемых
менеджерах, оператор на нём **авторизован**, позиция открыта и живая. При этом ни одна операторская
операция там физически не пройдёт — и не из-за одной причины, а из-за трёх независимых.

Опасность не в сегодняшнем состоянии (исполнение на сети выключено намеренно), а в том, что
включение выглядит как переключение одного флага `execute: true`, а на деле требует трёх шагов, ни
один из которых нигде не описан.

## Доказательство

**1. Оракул не привязан к менеджеру.**

```
get_manager_config 130 0x9f7E19B7A3fe5e767C515203446eb9A99A104970
→ "priceOracle": "0x0000000000000000000000000000000000000000"

oracle_status 130 0x9f7E19B7A3fe5e767C515203446eb9A99A104970
→ { "wired": false, "maxDeviationBps": null }
```

`BaseLPManager.sol:348-349` — гейт операторского свопа:

```solidity
address o = priceOracle;
if (o == address(0)) revert OperatorSwapGuardRequired();
```

Это не «оракул иногда не отвечает», а безусловный реверт любого операторского свопа.

**2. Оракул на сети развёрнут, но нужного фида в нём нет.**

`deployments/130.json` содержит `"oracle": "0xAC7966454B32006de29273094Ff0FCf8D367eF87"` — контракт
существует и сконфигурирован (4 события `FeedSet` от 2026-07-25, все с `heartbeat` 0x15180 = 86400,
агрегаторы `0xbd1cD1518e…` USDC, `0xC13f3E31…` BTC, `0xBcE70e19…` ETH, `0xdAd6f904…` UNI):

```bash
curl -sS "https://unichain.blockscout.com/api/v2/addresses/0xAC7966454B32006de29273094Ff0FCf8D367eF87/logs"
```

Управляемые валюты менеджера — USDC (`0x078D782b760474a361dDA0AF3839290b0EF57AD6`) и **USD₮0**
(`0x9151434b16b9763660705744891fA906F660EcC5`). В `script/oracle_feeds.json` секция `130` содержит
только `BTC / ETH / USDC / UNI / LINK` — **строки для USDT/USD₮0 в ней нет вообще**. Значит даже
после `setPriceOracle` своп по паре USDC↔USD₮0 упрётся в «нет референса» для второй ноги.

**3. На операторском кошельке нет газа именно на этой сети.**

```
get_status → chainId 130: "execute": false,
             balance { "eth": "0", "estimatedOps": 0 },
             managers[0].authorized = true
```

Состояние позиции при этом здоровое: диапазон `[-89, 111]`, текущий тик ≈ **+8** — позиция **в
диапазоне**, идл 0.14 USDC + 0.19 USD₮0 против ~9.6 USD в позиции (3.4 %, порог 20 % не задет).
Чинить «горит» нечего.

## Влияние

Прямой цены сегодня нет: исполнение на Unichain выключено осознанно и это записано в
`qa-workspace/quality/metrics.md`, позиция в диапазоне, суммы символические (~9.6 USD).

Цена отложенная и ровно в том месте, где её больнее всего обнаружить: если позицию решат вести
оператором, `execute: true` не заработает, и разбираться будут по факту молчащего реверта. Плюс
сигнала «менеджер под наблюдением, но неуправляем» в контуре нет — если позиция уйдёт из диапазона,
никто не подхватит её и никто об этом не узнает.

Severity выбрана нижняя из двух: чек-лист домена B прямо называет «фид не сконфигурирован для токена
активной позиции» аномалией **S2**. Взята **S3**, потому что исполнение на сети выключено намеренно
и этот факт зафиксирован — контур сейчас ничего пользователю не обещает. **Если `execute` переведут
в `true`, задача автоматически становится S2 и срочной.**

## Корень

Unichain разворачивали до того, как появился оракул-гейт (task_031/032, аудит 2026-07-18), и
пост-деплойный шаг «привязать оракул к менеджеру + залить фиды под его валюты» не был добавлен в
чек-лист деплоя. Косвенно на это указывает, что на Arbitrum тот же шаг сделан вручную
(`SetOracleFeeds.s.sol`, 2026-07-25) и его результат отличается: там `priceOracle` привязан.

Отсутствие USD₮0 в `oracle_feeds.json` — того же происхождения: файл собирали под BTC/ETH/USDC/UNI, а
стабильный менеджер на Unichain торгует пару, которой в нём нет.

## Что делать

Не «включить оператора на Unichain» — это продуктовое решение, его принимает человек. Задача в том,
чтобы включение стало однокнопочным и явным:

1. Добавить в `oracle_feeds.json` секцию `130` запись для USD₮0. Если Chainlink не публикует
   USD₮0/USD на Unichain — зафиксировать это в комментарии файла как известное ограничение сети,
   чтобы «почему нельзя» было написано там, где будут искать.
2. Оформить пост-деплойный шаг «привязать оракул» (`setPriceOracle`, owner-only) как часть скрипта
   деплоя или как явный пункт `script/README.md` — сейчас его нет ни там, ни там. Это и есть корень:
   шаг существует только в голове того, кто делал Arbitrum.
3. Дописать в `qa-workspace/quality/metrics.md` рядом с `Исполнение: выключено` **почему** выключено
   (нет привязки оракула, нет фида на USD₮0, нет газа) — чтобы следующий прогон дежурного не
   открывал это заново.

Пополнение газом в задачу не входит: пока исполнение выключено, газ там не нужен.

## Как проверить

```
oracle_status 130 0x9f7E19B7A3fe5e767C515203446eb9A99A104970
```

должен вернуть `wired: true` с ненулевым `maxDeviationBps`, а `propose_allocate` с пресвопом на этом
менеджере — собрать план, а не отдать `OperatorSwapGuardRequired`.

Если решено оставить сеть выключенной, проверка другая и такая же обязательная: в `metrics.md`
записана причина, а в `oracle_feeds.json` есть комментарий про USD₮0. Задача закрывается и так — но
не закрывается молча.
