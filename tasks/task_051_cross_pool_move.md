# task_051 — `moveLiquidity`: переставить ликвидность из пула в пул за один unlock

**Репозиторий:** `uniswap-smart-wallet` · **Ветка:** `task/051-cross-pool-move`
**Продукт:** `VolatileLPManager` (и наследник `OpenVolatileLPManager`). **`StableLPManager` не трогаем** —
у него 482 Б запаса EIP-170 и модель с зафиксированным на init диапазоном, в которую эта операция не
ложится.
**Номера 049/050 заняты** ссылками из `qa-workspace/quality/findings/INDEX.md` (provenance деплоя и
раскатка heartbeat-подбивки), поэтому эта задача — 051.

## Зачем

Сегодня «переложить капитал из пула A в пул B» — это две транзакции: `withdrawTo` на самого себя,
затем `allocate`. Цена:

* лишний `unlock` и лишние 21 000 газа intrinsic;
* второй проход сведения по union валют;
* **окно, в котором деньги лежат idle между двумя транзакциями** — позиция уже закрыта, новая ещё не
  открыта, доходность в это время нулевая, а состояние менеджера снаружи выглядит как «оператор что-то
  сломал»;
* каждый своп проходит оракульный гард отдельно, со своей ценой на своём блоке.

`recenter` (op 8) делает ровно нужную механику — снять → своп → добавить одним вызовом, — но заперт в
границах **одного** `poolId`. Задача снимает это ограничение.

## Что v4 разрешает (проверено)

Дельта в v4 ключуется парой **(адрес, валюта)**, а не пулом: `PoolManager._accountDelta` →
`currency.applyDelta(target, delta)` (`PoolManager.sol:368-378`). `modifyLiquidity` и `swap` защищены
только модификатором `onlyWhenUnlocked` (`:145-150`, `:187-192`), а `unlock` на выходе проверяет ровно
одно условие — `NonzeroDeltaCount.read() != 0 → CurrencyNotSettled` (`:104-114`). Сколько пулов
потрогали внутри — v4 не интересует.

Проверено тестом `test/CrossPoolUnlock.t.sol` (написан при разборе, 3 теста зелёные, вне контура
задачи — можно забрать в неё или удалить):

* снять из USDT/USDC fee 3000 и добавить в USDT/USDC fee 500 за один unlock: **2 ненулевые дельты на
  две валюты** (не на два пула), сведение одним проходом, через баланс контракта реально проехало
  **по 1 wei** каждой валюты — всё остальное схлопнулось внутри;
* снять из USDT/USDC → своп USDC→DAI в третьем пуле → добавить в USDT/DAI: **три пула, один unlock**,
  3 дельты, одно сведение;
* контрольный: два свопа в двух пулах и выход без сведения → `CurrencyNotSettled`.

Наш `_handleAllocate` уже устроен именно так (цикл по legs, один `_settleManaged()` в конце), так что
архитектурно ничего нового не вводится.

## Что делать

### 1. Новая операция

```solidity
uint8 internal constant OP_MOVE = 9;    // ALLOCATE_V=7, RECENTER=8 — 9 первый свободный

struct MoveParams {
    WithdrawStep[]      pulls;   // что освободить: salt + liquidityToPull (переиспользуем базовый тип)
    VolatileAllocLeg[]  adds;    // куда положить: пул, salt, диапазон, пре-своп, floor'ы
}

function moveLiquidity(MoveParams calldata p) external onlyAuthorized nonReentrant fixEtherBalance;
```

Обработчик в `_dispatchExtraOp`:

```
_handleMove(payload):
    for pulls:   _pullLiquidity(...)      // как в withdrawTo; полный вывод ⇒ _removeSalt
    for adds:    _allocateLegV(leg, byOwner)   // уже содержит пре-своп + _guardSwap + _addLiquidityV
    _settleManaged()                       // ОДИН проход по union валют
```

Ключевое: **никакого `recipient` в параметрах нет**. У операции нет пути наружу — всё, что не ушло в
новые позиции, остаётся на балансе менеджера. Это структурная гарантия, а не проверка.

**Минимальная версия — без отдельного массива `swaps[]`.** Пре-своп у `VolatileAllocLeg` уже есть, он
исполняется **в целевом пуле**, и этого хватает для основного сценария (тот же/пересекающийся набор
валют: другой fee-tier, другой диапазон, соседний пул с общей валютой). Кросс-парный переезд
(USDC/ETH → USDT/WBTC) требует свопа в **третьем** пуле — это форма `WithdrawSwap` из `withdrawTo`, но
ей нужен `minAmountOut`, которого там нет. Решение по этому — **после замера размера** (см. п. 4):
добавляем `RebalanceSwap[]` только если влезает.

### 2. Инварианты и проверки

* **Свопы оператора — fail-closed через оракул.** `_guardSwap(byOwner, ...)` на каждом свопе, ровно как
  в `allocate`/`recenter`. Владелец — без ограничений.
* **`minLiquidity` на каждом add** (уже в `VolatileAllocLeg`) и `minAmountOut` на каждом пре-свопе.
* **`ZeroLiquidity`** — добавление с `L == 0` отвергается (audit L-REG-1 / task_034), иначе плодим
  ghost-salt'ы.
* **`RangeMismatch`** — top-up существующего salt обязан совпасть по пулу и диапазону (уже есть в
  `_addLiquidityV`).
* **Полный вывод закрывает позицию** (`_removeSalt`), частичный — оставляет открытой.
* Пустые `pulls` или пустые `adds` — допустимы? **Нет:** оба массива непустые, иначе операция
  вырождается в уже существующие `withdrawTo`/`allocate` и только размывает семантику. Ревертим.

**Что операция сознательно НЕ гарантирует** (записать в NatSpec, не прятать):
оператор выбирает диапазон назначения и может оставить часть освобождённого капитала в idle вместо
переразмещения. Это degradation-of-yield, не кража: наружу ничего не уходит, а выбор диапазона у
оператора Volatile уже есть в `recenter`/`allocate`. Новая операция **не расширяет класс** его
полномочий — она расширяет их радиус: `recenter` переставляет в пределах одного пула, `moveLiquidity` —
между пулами настроенного набора. Набор пулов фиксируется владельцем на init и неизменяем.

### 3. События — не повторить task_047

**Поправка от 04.09 (проверено).** Ветка `task/047-fee-realisation-events` (`09ef12c`) существует и на
`origin`, но **изменений в `src/` в ней нет** — `git diff master..task/047-fee-realisation-events -- src/`
пуст, переписан только файл задачи. Значит «стекуемся на 047» невозможно: событие вводим здесь и
первыми, в формате, который 047 сам и рекомендует (вариант 1 — переиспользовать `FeesCollected`).

**Вторая поправка.** `_handleReinvest` (`StableLPManager.sol:277-311`) **не проходит** через
`_handleClaim` и `FeesCollected` не эмитит — предположение task_047, что реинвест «заодно» покрыт
claim-путём, неверно. Здесь не чиним: Stable в этой итерации не трогаем, но в 047 это надо записать.


Вытягивание ликвидности **реализует накопленные комиссии** — ровно та же механика, из-за которой
`recenter` обнуляет «пожизненные комиссии», не сообщая сумм (находка
`2026-08-22-recenter-erases-lifetime-fees`, task_047). Новая операция обязана сообщать, сколько
реализовала, **с первого коммита**:

* по каждому `pull` — реализованные `fees0/fees1` **брутто, до `_skimFees`**, через уже существующее
  `FeesCollected(bytes32 indexed salt, uint256 fees0, uint256 fees1)`
  (`abstract/V4PositionManager.sol:87`) — ровно так, как это делает claim-путь
  (`VolatileLPManager.sol:158`). Тогда потребители — `stablelp-ui/src/lib/data/positionHistory.ts`
  и индекс оракула — суммируют в один счётчик без единой правки, а нам не нужен второй тип события,
  то есть ноль лишних байт бюджета EIP-170;
* итоговое `LiquidityMoved(bytes32[] fromSalts, bytes32[] toSalts)` либо по-леговое `Moved(from, to, L)`
  — что дешевле по размеру;
* `IERC4906.MetadataUpdate(TOKEN_ID)` в конце, как у остальных мутаций.

Отдельно проверить, что новые топики попадут в сид грабера (`docs/db_struct/lp-manager-events.sql`) и
в `LIQUIDITY_MOVING_EVENTS` его хендлера — иначе `lp_positions` не увидит переезд.

### 4. Бюджет EIP-170 — гейт задачи

Текущие размеры (`forge build --sizes`, 03.09): Stable **24 094** (запас 482), Volatile **23 718**
(запас **858**), OpenVolatile **23 658** (запас 918). OpenVolatile наследует всё от Volatile, значит
любой прирост тратится дважды — по обоим лимитам одновременно.

Порядок работы: собрать минимальную версию → `forge build --sizes` → и только по остатку решать про
`RebalanceSwap[]`. Если минимальная версия не влезает: сначала выжимать переиспользование
(`_handleMove` должен звать существующие `_pullLiquidity`/`_allocateLegV`, а не копировать их тело),
и только потом обсуждать отдельную имплементацию. Отдельный продукт ради одной операции — плохой
размен, у нас уже три имплементации.

### 5. Тесты (`test/VolatileLPManagerMove.t.sol`)

1. **Основной сценарий:** позиция в пуле A (fee 3000) → пул B (fee 500), один вызов. Проверить:
   позиция A закрыта и salt выплюнут из `openSalts`, позиция B открыта с ожидаемой L, балансы токенов
   менеджера изменились только на пыль.
2. **Частичный переезд:** вынуть половину L — позиция A осталась открытой, B открыта.
3. **Top-up существующей позиции** в пуле B (тот же salt, тот же диапазон) — L суммируется.
4. **`RangeMismatch`** при top-up с другим диапазоном; **`ZeroLiquidity`** при add с нулевой L.
5. **Оператор без оракула** → `OperatorSwapGuardRequired`; **с оракулом-«pass»** → проходит;
   **с оракулом-«deviation»** → `OperatorSwapUnverified`. Владелец — проходит без оракула.
6. **Ничего не ушло наружу:** ни один адрес, кроме `PoolManager`, не получил токенов за операцию
   (сравнить балансы владельца, оператора и произвольного третьего адреса до/после).
7. **События:** реализованные комиссии сообщены суммами (см. п. 3), `MetadataUpdate` эмитится.
8. **Пустые `pulls`/`adds`** — реверт.
9. **Газовый бенчмарк** против двух транзакций. Опорные цифры уже сняты на моках (`forge`, 03.09):
   `withdrawTo` с одним pull ≈ **85 k**, `allocate` одной ноги ≈ **398 k**, плюс 2 × 21 k intrinsic;
   голый кросс-пульный мовер за один unlock — **406 k** (та же пара, другой fee-tier) и **492 k**
   (разные пары, со свопом через третий пул). Ожидаемая экономия — 60–100 k на операцию плюс
   исчезновение idle-окна. Цифры в задаче обновить фактическими.
10. Форк-тест на Base (`*.fork.t.sol`, env-gated `BASE_RPC`) — по остатку времени, не блокер.
